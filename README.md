# Car Parts Website — قطعه‌یار

Persian-first car-parts catalog, customer request, sourcing, quotation, order, payment, shipping and internal operations web application.

## Quick development start

```bash
./dev.sh
```

or `make dev`. The development runner starts Docker PostgreSQL, Spring Boot and Next.js, waits for health checks and opens `http://localhost:3000` on macOS. Useful commands: `make status`, `make logs`, `make stop`, `make reset-db`.

## Stack

- Java 21 + Spring Boot 4.1 + Spring Security
- Next.js 16 + React 19 + TypeScript
- PostgreSQL 18 + Flyway
- modular-monolith architecture
- Persian RTL responsive UI

## Business lifecycle

```text
Customer request (website / phone / WhatsApp / email / Instagram)
→ identify or create catalog product
→ inspect current product-price validity
→ current price exists: route to customer-price review
  OR price missing/expired: route to supplier inquiry
→ supplier quotation(s)
→ internal landed-cost review
→ customer quotation
→ agreement
→ sales order / payment
→ foreign purchase
→ international shipment
→ customs
→ local delivery
→ delivered / closed
```

A `workflow_case` is the operational spine. Products, requests, tags, supplier quotations, customer quotations, orders, payments, shipments, notifications and audit events connect to it.

## Accounts, manager zero and roles

New accounts require **name + username + phone + password + password confirmation**. Email is optional. Login accepts username, phone or email.

The first privileged account is **manager zero**:

```text
username: manager0
manager_level: 0
is_root: true
roles: SUPER_ADMIN + MANAGER
```

Only one root account can exist. Other managers cannot edit, disable, reset or change the roles of manager zero. Manager zero can change its own username/profile/password. `SUPER_ADMIN` is not assignable to ordinary accounts.

Ordinary managers use levels `1..99`; current levels are labels for future approval rules and never bypass role checks. A manager can create/edit/upgrade any non-root customer, admin, specialist or manager account from `/admin/users`.

Roles:

| Role | Main responsibility |
|---|---|
| `SUPER_ADMIN` | protected manager-zero/root authority |
| `MANAGER` | complete business pipeline + non-root account administration |
| `ADMIN` | day-to-day customer/product/tag/price-status operations without confidential costing |
| `PRODUCT_ADMIN` | product catalog and coding |
| `PROCUREMENT` | supplier inquiry and foreign purchasing |
| `FINANCE` | product/reference price, customer quotation, orders/payments |
| `SHIPPING` | shipment/customs/delivery |
| `SUPPORT` | requests/contact/content |
| `CUSTOMER` | own requests/orders/notifications |

Detailed authorization: `docs/ROLE_MATRIX.md`. Identity/history model: `docs/ACCOUNT_AND_HISTORY.md`.

## Authentication and registration

Passwords use BCrypt cost 12. Browser sessions use random 256-bit tokens; only SHA-256 token hashes are stored. Session expiry is written to PostgreSQL using an explicit SQL timestamp conversion. Authenticated mutations use CSRF protection; CORS is origin-restricted.

Customer self-registration: `/register`. Manager-created accounts: `/admin/users`. Email is optional; phone and username are unique/required for newly created accounts.

## Product code

Permanent code format:

```text
TT BB PB PK Q SSSS
```

| Segment | Width | Meaning |
|---|---:|---|
| `TT` | 2 | car type |
| `BB` | 2 | car brand inside selected car type |
| `PB` | 2 | part brand |
| `PK` | 2 | packaging |
| `Q` | 1 | quality |
| `SSSS` | 4 | serial per code combination |

Car-brand codes are scoped by car type, so code `01` can represent a sedan brand and independently code `01` can represent a truck brand. Java and PostgreSQL validate the type/brand relationship. The final 13-digit code is stored as text to preserve leading zeroes and is not regenerated by normal product editing.

Products also support product group, unit, physical profile, free-form code 1/2, status, reserved subjects and up to 10 image URLs.

The product form can create missing options inline. Vehicle brand creation requires its parent car type. Lookup deletion is deactivation, not destructive deletion.

## Product price validity

`product_prices` stores append-only price snapshots: amount, currency, validity range, status, note, creator and timestamp. Entering a new active price marks the prior active price `REPLACED`; it does not erase history. The UI defaults new prices to 60 days validity.

Request routing automatically checks the selected product:

- current price valid → `price-valid` automatic tag and manager/admin/finance notification;
- no price or expired price → `price-needed` automatic tag and manager/admin/procurement notification.

Public catalog shows only currently valid product prices. Internal price/history workspace: `/admin/products/{id}/operations`.

## Audit/background history

Flyway installs database audit triggers on core mutable tables. `audit_log` keeps before/after JSON for account/roles, customers, products/images, product code details/serial source, all lookup/code tables, product prices, requests/cases/tags, supplier/customer quotes, orders/items, payments and shipments.

Application-level rows add business actions such as product creation/edit, price set, role change, password reset, product attachment and customer-notification decision. Product history is viewable from `/admin/products/{id}/operations`; account history is viewable from `/admin/users`.

## Tags and notifications

Tags keep a source:

- `AUTOMATIC` — facts derived by the system: website request, sourcing, agreement, valid/missing price, shipping/customs, etc.
- `MANUAL` — staff context: urgent, VIP, offline agreement, special handling.

Manual tag changes are logged and can notify managers/admins.

`notifications` supports:

- in-app unread/read notifications for accounts (`/panel/notifications`);
- queued manual/WhatsApp/SMS/email messages for customers without accounts;
- events for new requests, product identification, price routing, quote sent, order creation and shipment status.

Product changes never silently message a customer. Manager/Admin/Product Admin chooses **notify customers** on the product operations page; the decision itself is audited.

## First privileged account

There is no fixed production password. For a new database:

```bash
export BOOTSTRAP_ADMIN_USERNAME='manager0'
export BOOTSTRAP_ADMIN_PHONE='+<your-phone>'
export BOOTSTRAP_ADMIN_EMAIL='optional@example.com'
export BOOTSTRAP_ADMIN_PASSWORD='<long-unique-password>'
export BOOTSTRAP_ADMIN_NAME='مدیر صفر'
```

For production also enable secure cookies, HTTPS and a restricted CORS origin.
